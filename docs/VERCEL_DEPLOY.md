# Публикация Freedom CQA в Vercel

Oracle отложен пользователем. Текущая цель — Vercel для интерфейса. Этот документ и `vercel.json` — конфигурация развёртывания, а не подтверждение уже работающего публичного сайта. Проверенный URL можно сообщить только после успешного Vercel deployment и открытия интерфейса.

## Что размещается в Vercel

Vercel собирает и раздаёт React/Vite-интерфейс: выбор диалога, расшифровку, объяснения, критерии, апелляции и демонстрационные данные. Загруженные в браузер новые диалоги остаются без AI-оценки, пока настоящий API не вернёт проверенный результат. При недоступном API приложение должно явно показывать локальный режим.

Корневая Node-функция `api/proxy.js` обеспечивает только защищённый proxy к настоящему API. FastAPI, GPU/Ollama, фоновые оценки и общая постоянная база — отдельный сервер. Не следует переносить текущую SQLite в эфемерную файловую систему Vercel Functions: это не обеспечит общую долговечную рабочую область. Наличие аккаунта Vercel не создаёт GPU или сервер модели.

## Настройки проекта

Импортировать **весь репозиторий**, а не только папку `frontend`. `frontend/src/data.js` использует общий `src/cqa/checklist.json`; корневая конфигурация сохраняет единственный источник правил.

| Поле             | Значение                                                   |
| ---------------- | ---------------------------------------------------------- |
| Root Directory   | Корень репозитория (`.`), не `frontend`                    |
| Framework Preset | Vite                                                       |
| Install Command  | `npm --prefix frontend ci --include=dev`                   |
| Build Command    | `npm --prefix frontend run build`                          |
| Output Directory | `frontend/dist`                                            |
| Node.js          | Поддерживаемая Vercel версия22/24; проект проверяется на24 |

Корневой `vercel.json` задаёт эти параметры. Он также разрешает долговременный кэш только для хешированных `/assets/*`, требует перепроверки HTML и добавляет базовые защитные заголовки. Приложение использует `#dialog/...`, поэтому для текущей навигации не нужен общий catch-all rewrite.

### Через интерфейс Vercel

1. Войти в свой аккаунт Vercel и открыть **Add New → Project**.
2. Выбрать репозиторий и ветку с актуальным дизайном. Стандартная ветка `main` может ещё не содержать незамёрженный PR.
3. Оставить Root Directory в корне и проверить значения таблицы.
4. Нажать **Deploy**, дождаться успешной сборки и открыть выданный deployment URL.
5. Выбрать один диалог, открыть аналитику, проверить подсветку доказательства и апелляцию. Отдельно проверить прямую ссылку `#dialog/<id>` после перезагрузки.

Если репозиторий не виден в импорте, установка GitHub-интеграции может требовать владельца репозитория. Альтернативно можно развернуть полную локальную копию через Vercel CLI в собственный проект Vercel: права администратора GitHub Pages для этого не нужны.

### Через CLI

Из **корня полной локальной копии**, где лежат `vercel.json`, `frontend` и `src`:

```bash
npx vercel login
npx vercel
# После проверки preview и при готовности опубликовать production:
npx vercel --prod
```

Войти через интерактивную авторизацию Vercel. Пароль и токен не добавлять в репозиторий или чат. При вопросах CLI выбрать свой scope/project и сохранить корень проекта. Перед production проверить, что публикуется текущая полная копия с нужным дизайном, а не другая папка или старая ветка.

Для команды, работающей в общей облачной среде, CLI выполняется после отдельной авторизации владельца Vercel; непроверенный или выдуманный домен нельзя выдавать за live deployment.

## Защищённое подключение настоящего API

Корневая Node-функция `api/proxy.js` обслуживает только конкретные маршруты CQA. Она не запускает Python/SQLite/Ollama внутри Vercel. Пока backend не настроен, `/api/health` и остальные допустимые маршруты возвращают **503 JSON с объяснением**, а не HTML, вымышленную готовность модели или придуманный балл.

Когда появится настоящий HTTPS backend с постоянной базой, в **Vercel → Project → Settings → Environment Variables** задать серверные значения:

| Переменная          | Назначение                                                                                                                     |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| `CQA_BACKEND_URL`   | Только origin настоящего API, например `https://api.your-domain.tld`; без `/api`, query-параметров, логина или пароля в URL    |
| `CQA_SITE_USER`     | Логин проверяющего для защищённой общей рабочей области                                                                        |
| `CQA_SITE_PASSWORD` | Пароль не короче 12 символов; хранить как серверный секрет                                                                     |
| `CQA_BACKEND_AUTH`  | При необходимости отдельный заголовок backend Authorization, например Bearer-токен или Basic-значение; только серверный секрет |

Не использовать префикс `VITE_` для этих значений: они не должны попадать в клиентский bundle. Не отправлять пароль, signed URL или токены в чат. После изменения серверных переменных выполнить новый deployment для нужного окружения.

`CQA_BACKEND_AUTH` аутентифицирует Vercel перед backend, а `CQA_SITE_USER/PASSWORD` — посетителя перед proxy. Это разные проверки. Функция не передаёт upstream ни браузерную Authorization, ни Cookie; upstream Authorization берётся только из серверной переменной. Сравнение логина/пароля использует одинаковые по длине SHA256-дайджесты и constant-time compare.

### Как войти

1. После настройки открыть `<реальный deployment URL>/api/health` в браузере.
2. В стандартном окне Basic Authentication ввести логин и пароль рабочей области. При ошибке будет401 с запросом входа; без настроенных site credentials остаётся503, чтобы общая база не стала публичной.
3. Вернуться на главную страницу этого же origin. Браузер использует авторизацию для последующих same-origin `/api/*` запросов.

Статический интерфейс может быть публичным демонстрационным экраном; реальные общие данные API защищены отдельно. Прямой backend также должен требовать авторизацию или быть доступен только через защищённый доступ: Vercel proxy не защищает отдельно открытый VPS.

### Маршруты и ограничения

- Разрешены только healthGET, workspaceGET/PUT, organizerGET с `group_id`, evaluatePOST и historyGET. Для других путей/методов функция возвращает404/405, не обращаясь к backend.
- Origin фиксирован серверной переменной и обязательно HTTPS. Пользователь не может выбрать адрес через query или тело. Redirect от backend не выполняется.
- Закодированный ID истории, включая `%2F`, сохраняется; query организаторов ограничен `group_id`.
- JSON-запрос и ответ ограничены 4 МиБ. Большой запрос отклоняется 413; private error body, адрес провайдера и секреты не возвращаются клиенту.
- Fetch прерывается через 55 секунд с 504. Конфигурация функции выделяет 60 секунд, чтобы успеть вернуть понятный ответ; тариф/настройки Vercel должны поддерживать эту длительность. Длинные многопроходные AI-задачи требуют асинхронных заданий/очереди и опроса статуса на настоящем сервере. Работа восьми агентов на CPU не обязана завершаться за 55 секунд; этот proxy такой срок не гарантирует. При 504 результат не подтверждён — сначала проверить историю реального backend.
- При конфликте версии workspace сохраняется статус409 и безопасная инструкция экспортировать свои изменения и обновить страницу; приватный текст backend не раскрывается.
- Все API-ответы имеют `Cache-Control: no-store`. Подписанная ссылка организаторов остаётся серверной переменной `CQA_DATA_URL` на Python backend.

Обязательна проверка реального импорта, критериев, N/A, отдельного грубого флага, истории и конфликтов после подключения. Наличие переменных окружения само по себе не доказывает точность модели.

Локальная проверка proxy без обращения к внешнему серверу:

```bash
node --test tests/vercel_proxy.test.cjs
```

Контрактные тесты проверяют 503/401, allowlist, server-only auth, JSON/path forwarding, размер, отсутствие утечки приватных ошибок и реальный AbortSignal по 55-секундному таймеру. Fetch в этих тестах замокан: это не проверка качества AI.

## Проверка и откат

- Сборка должна завершиться без missing `src/cqa/checklist.json`; такая ошибка означает, что загружена только папка frontend или неверно выбран Root Directory.
- Проверить правильный логотип, тёмную тему, выбор диалога, восемь критериев и отсутствие ошибок JavaScript.
- Не трактовать отсутствие server API как пустой UI или как успешную модельную оценку: при offline ожидается понятный статус и доступный интерфейс.
- Предыдущий успешный deployment сохраняется в Vercel Deployments. Вернуться к нему через доступное в аккаунте действие rollback/promote; эта операция откатывает frontend, а не внешнюю базу и не backend.

## Источники

Проверен официальный пример Vercel для Vite и ссылка на CLI deployment: https://github.com/vercel/vercel/tree/main/examples/vite-react .

Официальные справочники: https://vercel.com/docs/frameworks/frontend/vite и https://vercel.com/docs/project-configuration . Актуальные ограничения проекта и тарифа следует проверять в собственном кабинете; лимиты и бесплатность здесь не гарантируются.

Маршруты `/api/*` направляются явным rewrite в `api/proxy.js`. Внутренний `__cqa_path` сверяется с исходным путём и не передаётся в backend; это сохраняет вложенные ID истории и query группы организаторов.
