# Phase 3 performance — реальные измерения 2026-11-07

Модель: установленная `qwen3:4b`, Q4_K_M, digest `359d7dd4bcda`.
Windows, Python 3.12, RTX 3060 Laptop 6144 MiB, RAM около 31.26 GiB.
Новые модели не скачивались; внешних/платных LLM-запросов не было.
Все входы — один фиксированный синтетический RU-разговор из трёх реплик
(с различными synthetic IDs для параллельной партии), официальный чек-лист из 8
критериев. Никаких приватных разговоров в артефактах нет.

Машинные результаты: [JSON с per-job/per-call telemetry](phase3-artifacts/performance.json),
[CSV сравнения](phase3-artifacts/performance.csv).

В каждом HTTP-вызове одна попытка, retries=0. Уменьшенный context/output и одна
из параллельных оценок дали `validation_error`: JSON был декодирован, но доменная
схема/ответы/доказательства не прошли обязательную проверку. Evaluation для этих
jobs отсутствует. Raw failed output не сохранялся, поэтому более узкую причину
постфактум не придумываем. Это реальные отказы, включённые в знаменатель.
В последнем тесте получено ровно 1024 выходных токена при лимите 1024;
ответ отклонён как `invalid_output`, результат не сохранён. Ускорение до 23.4 s
не даёт пригодной оценки. Во всех пяти сценариях: 3/6 успешных jobs, 3 отказа,
7 LLM-вызовов. Browser smoke учитывается отдельно.

Успешный полный Critic: Evaluator 174.159 s, Critic 227.384 s, job 401.564 s,
ожидание worker 0.081 s. Первый вызов input/output 2190/2031, второй 4178/1998.
Циклических повторов нет — ровно два вызова, оба прошли validation.

RAM — вся система, VRAM — сумма измеренных NVIDIA GPU, а не исключительно модель
или Python process. Другие приложения и тесты влияют на цифры; они не доказывают
memory regression. Сэмплирование примерно каждые 2 s, включает запуск сервера.
Load — настоящий `load_duration` ответа Ollama, не гарантированно cold load:
модель намеренно не выгружалась между запусками. Все unavailable measurements
остаются null. В JSON есть duration/usage/attempts каждого вызова и safe error code.

`ollama ps` подтвердил CPU/GPU offload: при 16384 — около 21%/79%, при 24576 —
около 37%/63%; это распределение runtime, не процент загрузки GPU.
При parallel=2 второй вызов ждал внутри Ollama: его provider duration 182.776 s
при eval duration 77.944 s. Увеличение client concurrency не дало доказанного
выигрыша в числе валидных завершений на этой машине.

Практический выбор для локального demo — прежняя конфигурация 16384/4096,
один worker / LLM_CONCURRENCY=1, явно один проход. Она сохранила полный вход,
дала валидный результат и дополнительно дважды прошла browser smoke (88.04/90.79 s).
14336/3072 быстрее в этом замере, но её валидность не подтверждена; она не стала
настройкой demo. Critic 24576/4096 реально работает, но стоит около 6.7 минут на
этом коротком разговоре. Решение о семантической пользе Critic — за участником №2.

Для baseline наблюдалось около 0.677 нового валидного job/min. Простая
экстраполяция 65 × измеренная стоимость — около 95.9 минут для *таких же коротких
синтетических входов*. Для Critic аналогичная арифметика даёт около 7.3 часа.
Это не прогноз реального набора: выборка мала, длина и language mix другие,
валидность ответов не гарантирована, более длинный контекст меняет offload.
В CLI ETA рассчитывается из измеренной пропускной способности, cached jobs в неё
не включаются. Отдельный 65-task mock smoke не используется как LLM benchmark.

Повторить из корня (Ollama уже запущена, модель установлена):

```powershell
.venv\Scripts\python examples/cqa_performance.py --context 16384 --output-limit 4096
.venv\Scripts\python examples/cqa_performance.py --context 14336 --output-limit 3072
.venv\Scripts\python examples/cqa_performance.py --context 24576 --output-limit 4096 --critic
.venv\Scripts\python examples/cqa_performance.py --context 16384 --output-limit 4096 --parallel 2 --count 2
.venv\Scripts\python examples/cqa_performance.py --context 12288 --output-limit 1024
```

Запускать последовательно, без конкурирующих inference. Каждый процесс создаёт
отдельную `.runtime/performance/<UTC timestamp>/` с конфигурацией, SQLite,
JSON/CSV report, ресурсными сэмплами и безопасным server log. В CLI report
содержимое разговоров отсутствует; benchmark SQLite содержит только synthetic
fixture. Script фиксирует текущий git revision для новых запусков. Изменения
между измерениями касались telemetry/errors/CSV/readiness, семантические инструкции,
validation и scorer во всех сравнениях оставались теми же.

Замеры не являются accuracy benchmark. Нет эталонной разметки и статистически
значимого сравнения: не следует приписывать причину различия оценок контексту или
конкуренции по этой маленькой выборке. Обязательные проверки ради скорости не
отключались; транскрипт не обрезался.
